# InfraSWE R10：v0.1 发布后的 10 个历史 PR 合同补测

更新时间：2026-09-02 15:53 +08:00
协议：`historical-pr-blind-case-contract-v0.1-r10-10`

## 结论

InfraSWE v0.1 发布完成后，R10 从既有 outcome-free discovery lock 中选择了 10 个从未在
R1–R9 使用过的 PR，每个项目 1 个。选择阶段只看标题、changed paths、规模和精确 SHA；
随后先冻结逐案合同，再读取 diff、执行 exact base/head probe、锁定机器判断，最后才揭盲
PR 状态与 review。

本轮继续使用 ordered explainable contract，不使用 learned model、trained weights、加权总分
或强制两极化。锁前判断为：

- `accept_with_scope`：7；
- `revise`：3；
- `reject` / `unresolved`：0。

揭盲为 4 merged、1 closed-unmerged、5 open。4 个真正 merged 的 PR 全部在锁前得到
`accept_with_scope`；3 个 `revise` 当前全部未合并。

按严格三分类 disposition oracle，结果是 4/10：oracle 为 4 accept、0 revise、6 reject，
而机器保留了 3 个 revise。把 `revise` 与 `reject` 都映射为“不接收方向”后，二分类为 7/10。
两个数字都保留：前者衡量标签完全一致，后者衡量 merge direction，不用一种口径掩盖另一种。

## 1. 冻结链

```text
outcome-free R8 discovery pool
  -> R10 ten-case selection lock
  -> source inspection 前 case-specific test-plan lock
  -> exact base/head acquisition + changed-path parity
  -> nvcc / real PyTorch / AST / parser-state probes
  -> ordered machine judgment lock
  -> outcome/review reveal
  -> disposition-oracle audit
```

## 2. 汇总口径

| 指标 | 结果 | 解释 |
|---|---:|---|
| merged PR 被机器接受 | 4/4 | 所有真实 merged 均为 `accept_with_scope` |
| 机器 revise 当前未合并 | 3/3 | 1 closed-unmerged、2 open |
| 严格三分类 oracle match | 4/10 | `accept_with_scope→accept`、`revise→revise`、`reject→reject` |
| 二分类 merge-direction match | 7/10 | `revise` / `reject` 都映射为 reject direction |
| strict final-head reviewer 可审计 | 1/10 | 仅 FlashInfer #3918 满足严格资格 |

严格 oracle 延续既有约束：merged=accept，closed-unmerged=reject；只有 30 天内、final-head 有
独立实质反馈且 14 天内仍活跃的 open PR 才是 revise，其余 open=reject。slash command、bot
和作者自己的评论不算实质 reviewer feedback。

R10 明确不产生 0–100 加权分，因此不能诚实地审核“merged 分数是否 ≥85”。本轮只报告
4/4 merged 的定性接受，不在揭盲后补写 85+ 数字。

## 4. 三个阻塞性发现

### DeepGEMM #310：文本变化不是语义变化

base：

```python
(x.view(torch.int) & ((1 << 23) - 1) == 0).all()
```

head：

```python
((x.view(torch.int) & ((1 << 23) - 1)) == 0).all()
```

Python 运算符优先级已把 base 解析为相同结构。两棵 AST 完全一致，真实 PyTorch 对 valid 和
nonzero-mantissa controls 的行为也一致。该 PR 没有 direct regression，且冻结合同中的
zero/all-ones exponent controls 仍被接受。因此不是“代码更清楚就算修复”，机器锁为 revise。

阻塞码：

- `DEEPGEMM_PRECEDENCE_PATCH_SEMANTIC_NOOP`；
- `DEEPGEMM_UE8M0_EXPONENT_BOUNDS_UNENFORCED`；
- `DEEPGEMM_PACK_UE8M0_DIRECT_REGRESSION_MISSING`。

### Liger #1289：错误信息改善，但 guard 可被优化删除

head 在普通解释器模式下确实更早、也更可操作地解释未 materialize 的 ZeRO-3 weight；正向
vocab 邻值也没有变化。但输入约束使用 Python `assert`。同一 exact function 以
`compile(..., optimize=2)` 执行时，assert 被删除，V=0 再次触发原始 ZeroDivisionError。
冻结合同要求显式、稳定的 domain policy，所以判断是 revise，而不是把普通模式样例通过外推
到所有受支持运行方式。

阻塞码：`LIGER_ZERO_VOCAB_VALIDATION_USES_REMOVABLE_ASSERT`。

### vLLM #48705：修复了已知 chunk，但尚未获得流式单调性

该 patch 去掉 mid-stream `json.dumps()` 的临时右花括号，并从 raw length slicing 改为 common
prefix；因此官方两键、三键测试和大多数冻结分割点通过。但当 chunk 落在 escape、key 或
delimiter 的某些内部边界时，parser 会先发出后来需要回撤的片段，而流式协议只能追加，不能
撤销。head 相比 base 明显改善，但没有满足“所有冻结 chunk reconstruct exactly once”。

阻塞码：`VLLM_FUNCTIONGEMMA_STREAM_BOUNDARY_CORRUPTION_REMAINS`。

## 5. reviewer 与 disposition 解释

- FlashInfer #3918 是唯一 strict final-head reviewer 样本。reviewer 给出 LGTM，同时要求检查
  其他 `.numel()` / `.size()` / `.element_size()` / `.clone()` 对输入的直接调用。机器合同独立
  覆盖了本次 changed batching 与 size guard，并把完整 GPU profiling 留为范围项；方向一致。
- TorchTitan #3862 的 reviewer 讨论了 compile、Helion 与 DTensor 的更广组合，并要求另建
  tracking issue。机器没有把 CPU stride probe 外推为完整 GPU stack 证明，保留了同类范围项。
- CUTLASS、FlashAttention、SGLang 三个机器 accept 仍处于 open，且没有独立活跃 final-head
  review，所以按严格 disposition oracle 都是 reject。这三项构成二分类的 3 个 false positive；
  当前没有 closed-unmerged 技术反证，不能把“open”改写成“已经验证会合并”。
- Liger closed-unmerged，但没有可用的独立 reviewer 文本确认 `assert -O` 问题；只能说机器
  revise 与 reject direction 一致，不能宣称 reviewer 命中。
