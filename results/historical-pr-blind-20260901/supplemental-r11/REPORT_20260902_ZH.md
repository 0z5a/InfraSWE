# R11：20 个历史 PR 的 check/reject 盲测

## 结论

R11 达到了本轮预先约定的提交门槛：在同一批 20 个 PR、同一组冻结证据上，新的
repairability triage 将 exact label 从旧路数的 `5/20`（25%）提高到 `10/20`（50%），
提升 25 个百分点。

改善集中在本轮目标 check/reject 区分：8 个机器非 accept 案例中，旧路数会全部输出
check，exact 为 `0/8`；新规则输出 2 check、6 reject，exact 为 `5/8`。排除其中两个真实
merged 案例后，6 个真实非 accept 案例命中 `5/6`；机器 reject 的 precision 为 `5/6`
（83.3%）。因此可以提交，但不能把结果描述成分类问题已经解决。

本报告从现在起统一使用 `check`。R11 的判断锁在用户提出改名之前已经完成哈希冻结，
所以原始锁仍含旧 wire label `revise`；审计层将它无损映射为 `check`，分组和判断均未改变。

## 结果摘要

| 指标 | R10 式同队列基线 | R11 | 变化 |
|---|---:|---:|---:|
| Exact label | 5/20（25%） | 10/20（50%） | +25 pp |
| Binary accept/non-accept | 11/20（55%） | 11/20（55%） | 0 pp |
| 8 个冻结非 accept 的 exact | 0/8 | 5/8 | +62.5 pp |
| 6 个真实非 accept 的 check/reject exact | 0/6 | 5/6 | +83.3 pp |
| Reject precision | N/A（0 个 reject） | 5/6（83.3%） | 可测 |
| Check precision | 0/8 | 0/2 | 无正例可验证 |

R10 原始队列是 `4/10` exact、`7/10` binary；R11 是 `10/20` exact、`11/20` binary。
跨队列看 exact 高 10 个百分点、binary 低 15 个百分点，但样本不同，这不是因果比较。
同队列对照才是本轮“有提升”的依据，而且它只改变 check/reject，不改变 accept/non-accept。

Oracle 分布为 7 accept、0 check、13 reject。由于本轮没有符合“30 天内的新 PR、当前 head
有近期真人评审”条件的 check 正例，R11 只能证明 reject 分离能力提高，不能证明 check 的
precision 或 recall 已经可靠。

7 个真实 merged PR 中，机器 accept 5 个。另两个分别被判 check 和 reject。因此本轮没有
达到“所有 merged 都 accept”的理想状态；同时 R11 明确禁用权重分数，不能审计数值 85 分
门槛，不能用类别结果冒充数值评分。

## 盲测协议

1. 先冻结 10 个项目各 2 个、共 20 个未在 R1–R10 使用过的 PR。选择阶段只读取标题、
   路径、规模和精确 base/head SHA，不读取状态、merge、CI 或 review。
2. 在查看 diff 内容前冻结每例 claim、问题、执行层级和 accept/check/reject 规则。
3. 获取精确 base/head 文件，验证 changed-path parity，并在统一环境执行 20 个案例探针。
4. 根据 case contract 和冻结的 repairability policy 生成机器判断锁；随后才调用 GitHub API
   揭示 disposition 和人类 review。
5. 用同一 disposition oracle 审计：merged 为 accept；closed-unmerged 为 reject；只有满足
   新 PR 与近期当前-head 真人评审条件的 open PR 才是 check，其余 open PR 为 reject。

所有 20 个最终探针均为 pass，统一环境为 Python 3.12、PyTorch 2.11.0+cu128、CUDA 12.8、
2×NVIDIA A100-SXM4-40GB。Liger mixed-dtype 路径在真实 CUDA 上执行；其余案例按冻结计划
执行精确源码隔离、AST、状态机、并发调度或边界矩阵。解盲时 20 个 current head 均与锁定
head SHA 一致。

## R10 经验带来的有效变化

R10 把 DeepGEMM #310 的 semantic no-op、Liger #1289 的单点可修复缺口和 vLLM #48705 的
跨多族 parser corruption 都归为 check。R11 将 check 收窄为：主方向已经被执行证据证明、
没有基线回归或安全/完整性风险、修复面有界、存在可执行闭环、且最多剩一个 failure family。

以下门槛在 R11 得到正向验证：

- 核心 claim 为假：DeepGEMM #327 正确 reject。
- 新增基线回归：verl #7046 正确 reject。
- 完整性风险或多族残留：FlashInfer #3930、vLLM #48755 正确 reject。
- 无界 ownership/design 问题：CUTLASS #3352 正确 reject。

六个 reject 中五个命中，说明不再把所有技术失败都塞进模糊的中间类别是有效的。

## 暴露的问题与下一轮假设

两个非 accept 误判给出的教训不同：

- Megatron #5726 是 contract 膨胀。PR 的明确 claim 只是默认 modes 的基数；冻结计划把原有
  malformed explicit input 校验也设成阻断项，导致一个真实 merged 修复被降为 check。以后要
  分开“本 PR 必须满足的 acceptance contract”和“值得后续加固但不阻断的 hardening”。
- vLLM #48754 是范围外推过度。该改动正确解决版本号式 dotted local name，但冻结测试要求
  一个无 registry/filesystem 上下文的语法 helper 解决所有已注册 dotted name，导致 false
  reject。需要从标题和具体入口冻结最小 claim，不能把更理想的架构设计冒充该 PR 的合并门槛。

DeepGEMM #337 说明仅有 benchmark 自建 closure probe 不足以预测 disposition check：实现本身
正确，但没有候选自带直接回归，且 PR 已长期 open。下一轮可前瞻检验“check 必须有候选自带、
能在当前 head 关闭唯一残留问题的测试；只有 evaluator probe 时倾向 reject”。这只是 R11
解盲后的新假设，不能回写本轮判断。

accept/non-accept 的 55% binary 是本轮明显短板：七个技术 contract 通过的案例因长期 open 或
closed-unmerged 被 disposition oracle 判 reject。新 triage 与同队列基线在 binary 上完全相同，
所以它既没有造成这项下降，也没有解决它。技术正确性与项目 disposition 仍需分层报告。
