# R12：12 个通信类历史 PR 的双卡盲测

## 结论

R12 达到“有提升再提交”的预设门槛。在同一批 12 个通信类 PR、同一组冻结证据上，
communication case-contract triage 的 exact label 为 `7/12`（58.3%），旧路数“contract
通过则 accept，否则一律 check”为 `3/12`（25%），提升 33.3 个百分点。

改善仍集中在 check/reject：8 个旧路数非 accept 案例中，旧路数 exact 为 `0/8`；新规则
为 `4/8`。其中机器给出的 5 个 reject 有 4 个最终是 reject，precision 为 `4/5`（80%）。
因此本轮可以提交，但不能把它描述成 accept/non-accept 已经改善：两种路数的 binary 都是
`8/12`（66.7%）。

远端确实是 `2×NVIDIA A100-SXM4-40GB`。此前无法连接是 SSH 默认选错私钥，不是单卡或少卡。
修正 identity 后，双 rank NCCL、TorchTitan bucket 数值等价和精确候选 DDP graph 路径均已执行。
SGLang #31290 仍 unresolved，是因为冻结 contract 指定 Intel XPU/XCCL；两张 NVIDIA A100
不能替代 Intel XPU backend。

本轮所有新判断均直接使用 `check`，没有生成新的 `revise`。R12 没有使用权重分数，因而不
伪造 85 分门槛：本报告只审计离散 disposition label，不能声称 merged PR 已取得正式
`>=85` ProjectFit。

## 结果摘要

| 指标 | 同队列旧路数 | R12 | 变化 |
|---|---:|---:|---:|
| Exact label | 3/12（25%） | 7/12（58.3%） | +33.3 pp |
| Binary accept/non-accept | 8/12（66.7%） | 8/12（66.7%） | 0 pp |
| 8 个冻结非 accept 的 exact | 0/8 | 4/8 | +50 pp |
| 5 个真实非 accept 且冻结非 accept 的 exact | 0/5 | 4/5 | +80 pp |
| Reject precision | N/A（0 个 reject） | 4/5（80%） | 可测 |
| Check precision | 0/8 | 0/2 | 无正例可验证 |

冻结判断分布为 4 accept、2 check、5 reject、1 unresolved；oracle 分布为 6 accept、0 check、
6 reject。6 个 merged 中只有 3 个被机器直接 accept，另有 2 个 check、1 个 reject。没有
check oracle 正例，所以本轮只能再次证明“从模糊中间态中分出明确 reject”有效，不能证明
check precision 或 recall 已可靠。

作为非因果参考，R10 原始不同队列为 `4/10`（40%）exact、`7/10`（70%）binary；R12 分别
高 18.3 个百分点和低 3.3 个百分点。样本不同，不能把这组跨队列差值当成策略收益。

## 盲测协议

1. 从既有 outcome-free discovery lock 中冻结 12 个此前 R1–R11 未评分的通信类 PR；选择
   阶段只使用标题、changed paths、规模和精确 base/head SHA，不读取状态、merge、CI 或 review。
2. 在读取 source diff 前冻结逐例 claim、通信风险、执行层级、问题矩阵和三分规则。
3. 获取精确 base/head 文件并验证 path parity，在统一双 A100 环境运行 12 个候选探针。
4. 额外运行双 rank NCCL 通信探针，以及 TorchTitan #3821 精确候选 commit 的 DDP graph
   export/bucketing 路径。
5. 先生成逐例机器判断及哈希锁，再揭示 GitHub disposition 和人类 review。
6. Oracle 沿用已冻结规则：merged 为 accept，closed-unmerged 为 reject；只有新 PR、当前 head
   有明确且近期真人评审的 open PR 才为 check，其余长期 open PR 为 reject。

`probes/*.json` 中的 `probe_status=pass` 表示探针按冻结协议成功执行，并不表示相应 PR 被判
accept。12/12 探针执行成功，解盲时 12/12 current head SHA 与冻结 SHA 相同；最终机器判断
仍由探针事实和逐例 contract 决定。

## 双卡实测

标准候选探针环境为 Python 3.12、PyTorch 2.11.0+cu128、CUDA 12.8、NCCL 2.28.9、
`2×NVIDIA A100-SXM4-40GB`。独立双 rank 通信探针得到：

- NCCL 两 rank smoke 通过；Megatron #5720 的 destination-CP SUM 精确到达目标 leader。
- TorchTitan #3821 将 6 次同 group、同 op 的独立 all-reduce 合成 1 个 bucket 后，两 rank
  全部输出逐元素完全相等，`max_abs_diff=0`。
- vLLM #48763 的旧 `2H` gather 与新 `H` gather 在每 rank token 数 1、16、64、256 上均
  逐元素完全相等；通信 payload 减少 50%，rank 0 median latency 分别下降约 24.8%、30.0%、
  40.1%、52.9%。这是 communication-path microbenchmark，不是完整模型 5% E2E 复现。

TorchTitan #3821 还在精确 head `63a758ccc3af6023337a73331473eed24e990bff` 上，使用
PyTorch `2.15.0.dev20260901+cu130` 运行候选自身 DDP graph 路径；没有 compatibility shim。
两 rank 都把 6 个 parameter all-reduce bucket 为 1 个，graph lint 和候选 contract 均通过。

## 通信类判断经验

### 1. 先证明 counterexample 在生产通信域可达

通信代码的任意 tensor shape、任意 process group 和任意 helper root 并不等于支持域。R12 两个
merged 误判都暴露了这个问题：

- SGLang #31311 的 `5→3` 非整除 shrink 是 evaluator 构造的边界；没有先证明 LongCat 的
  token/TP/EP 拓扑能产生该几何，就不应把它升级成 merge blocker。
- TorchTitan #3827 的“传入非 TP group”与“root module 本身就是 FusedSwiGLU”同样缺少从实际
  generator/RL 入口到失败点的 reachability proof。源码注释和调用安装点反而指向 TP 同 rank-set
  与非 root FusedSwiGLU。

下一轮应在冻结 contract 中加入明确顺序：launch/config 可行性 → call-site reachability →
rank/shape/group invariant → 数值或 deadlock oracle。无法证明可达的 synthetic counterexample
只能记为 non-blocking hardening，不能单独触发 reject。

### 2. 候选正文属于证据，不属于 outcome 泄漏

R12 的 source bundle 只收 exact changed files，漏掉了候选作者在 PR body 中提供的测试：

- vLLM #48763 正文包含 TP4 serving 命令、main/now 结果和吞吐数据；机器却因“候选无 paired
  benchmark”给了 check。
- TorchTitan #3827 正文包含 default 与 spmd_types 的 10-step bitwise 对比，以及启用
  FusedSwiGLU 的重复运行。
- SGLang #31311 正文包含 TP16/EP16、DeepEP normal/low-latency 的 accuracy 结果。

这些内容在 PR 创建时由候选方提供，本身不是 merge、review 或 CI outcome。后续 blind pack
应在判断前通过只投影 title/body/head SHA 的接口获取并哈希冻结 PR body，同时继续排除 state、
merged、review、label 和 CI 字段。性能 claim 应按“候选 paired E2E → evaluator microbenchmark
→ 精确模型复现”分层，不应把缺少 diff 内测试误写成缺少候选证据。

### 3. 技术 contract 与项目 disposition 要并列报告

TorchTitan #3821 是最清楚的反例：精确候选 graph、双 rank NCCL 数值和候选 HSDP/DDP 测试均
通过，但该 PR 长期 open，按用户指定 oracle 必须 reject。这里不是技术通信判断错误，而是
“技术可接受”不能预测“项目最终处置”。以后应同时保留：

- `technical_contract`: pass/fail/unresolved；
- `disposition_prediction`: accept/check/reject；
- 两者不一致时的 `governance_gap`，而不是回写技术证据迎合 outcome。

### 4. 双 GPU 只解决一部分硬件充分性

双 A100 能覆盖 NCCL、常规 CUDA、distributed graph 和通信 microbenchmark，但不能覆盖 Intel
XPU/XCCL、SM90 专属 kernel 或 Blackwell 专属 launch。判断 `unresolved` 时应记录缺的是 backend、
architecture 还是卡数；“有两张卡”不等于所有通信实现都可执行。

### 5. check 仍须前瞻验证

本轮两个 check 最终都 merged，而 oracle 仍没有 check 正例。这提示通信性能/拓扑修复在主
方向、真实域和候选证据都成立时，当前 contract 可能偏保守；但这是解盲后假设，不能回写 R12
锁。必须在下一批新样本上前瞻验证 reachability 与 body-evidence 规则后，才能修改正式分类器。
