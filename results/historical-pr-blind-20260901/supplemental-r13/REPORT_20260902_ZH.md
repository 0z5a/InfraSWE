# R13：29 个训练类历史 PR 的双卡盲测

## 结论

R13 达到“有提升再提交”的预设门槛。在同一批 29 个训练类 PR、同一组冻结证据上，
training case-contract triage 的 exact label 为 `8/29`（27.6%），旧路数“contract 通过则
accept，否则一律 check”为 `5/29`（17.2%），提升 10.3 个百分点。

提升仍只发生在 check/reject 分离：机器给出的 4 个 reject 有 3 个最终为 reject，precision
为 `3/4`（75%）；旧路数没有给出任何 reject。两种路数的 accept/non-accept binary 都是
`14/29`（48.3%），没有改善。冻结判断为 11 accept、12 check、4 reject、2 unresolved；
oracle 为 14 accept、0 check、15 reject。

这批成熟历史 PR 没有任何 oracle check 正例，因此 12 个技术 check 的 disposition precision
为 0。它们不是无意义结果：多例确实定位了有明确 closure test 的边界缺口，但按用户指定的
历史处置 oracle，长期 open 或 closed-unmerged 必须归 reject，merged 必须归 accept。下一轮
必须并列输出 `technical_contract` 与 `disposition_prediction`，不能继续把技术上的“尚需一项
验证”直接当成项目最终的 check。

远端为 `2×NVIDIA A100-SXM4-40GB`。本轮执行了精确候选源码测试、双 rank NCCL、Megatron
deferred DP-outer reduction、slime TP2 log-prob/entropy/gradient 与显存模型、verl CP shape 和
NCCL CPU broadcast 反例。R13 没有使用权重分数，不能声称 merged PR 已取得正式 `>=85`
ProjectFit；这里只审计离散标签。

## 结果摘要

| 指标 | 同队列旧路数 | R13 | 变化 |
|---|---:|---:|---:|
| Exact label | 5/29（17.2%） | 8/29（27.6%） | +10.3 pp |
| Binary accept/non-accept | 14/29（48.3%） | 14/29（48.3%） | 0 pp |
| 18 个冻结非 accept 的 exact | 0/18 | 3/18 | +16.7 pp |
| Reject precision | N/A（0 个 reject） | 3/4（75%） | 可测 |
| Check precision | 0/18 | 0/12 | 无 oracle 正例 |
| Merged 中机器直接 accept | 5/14 | 5/14 | 0 |

R13 的发布理由是目标指标 check/reject exact 有前瞻改善，不是整体 accuracy 已经足够高。
`27.6%` exact 与 `48.3%` binary 都说明 disposition 分类仍需显著改进。

## 队列构成与盲测协议

队列共 29 个训练类 PR：原始 14 个，加 Megatron、slime、verl 各 5 个扩展案例；项目分布为
FlashAttention 1、Liger-Kernel 3、Megatron 9、slime 5、TorchTitan 3、verl 8。

1. 选择阶段只使用标题、changed paths、变更规模、创建时间与精确 base/head SHA；不读取
   state、merge、CI、label、review 或 comment。
2. 在读取 diff/source 前冻结逐例 claim、风险矩阵、执行层级与 closure test；扩展队列与原始
   队列组合后重新生成唯一 29-case selection/test-plan lock。
3. 获取精确 base/head 文件并验证 path parity；对 29 例运行 case-specific probe，并在可用的
   精确 upstream worktree 中执行候选自带测试。
4. 在两张 A100 上运行双 rank 训练通信/数值探针；硬件或依赖无法覆盖的 contract 记
   unresolved，不把静态推断冒充运行证据。
5. 先冻结 29 个机器判断及所有 evidence binding，再读取 GitHub disposition 与真人 review。
6. Oracle 沿用冻结规则：merged 为 accept，closed-unmerged 为 reject；只有 30 天内且 14 天内
   有明确真人评审的 open PR 才可能是 check，其余长期 open PR 为 reject。

解盲时 29/29 current head SHA 与 selection lock 一致。揭示结果为 14 merged、8
closed-unmerged、7 open；7 个 open 均不满足新近在审条件。所有 superseded 的测试启动失败和
环境配置错误继续保留在原始 evidence 中，最终判断只引用显式标为 authoritative 的修正记录。

## 双卡与精确候选实测

标准环境为 Python 3.12.14、PyTorch 2.11.0+cu128、CUDA 12.8、NCCL 2.28.9，GPU 为
`2×NVIDIA A100-SXM4-40GB`。关键结果：

- 双 rank NCCL smoke 通过。
- Megatron #5743 deferred 与 eager 数值逐元素一致；每 rank DP-outer collective 从 3 次减为
  1 次。
- slime #2152 TP2 log-prob 完全一致，entropy 最大绝对误差 `2.38e-7`，BF16 gradient 最大
  绝对误差 `0.00258`；建模 scratch peak 从 100,668,416 降至 33,559,552 bytes，约减少
  66.7%。但 retained graph 第二次 backward 因原地 negation 触发 version-counter 错误。
- verl #7012 在两 rank 上由 base teacher local length 4 / student 6 修复为 head 6 / 6。
- verl #6996 在默认 NCCL group 广播 CPU tensor，两 rank 均复现
  `No backend type associated with device type cpu`；CUDA tensor 对照成功。
- TorchTitan #3897 精确 head 含未解决 merge-conflict marker，Python 编译直接失败。
- Megatron #5714 候选自带 TP2/DP1 测试在两 rank 上失败：产生 2 shards，而断言期望 1。
- FlashAttention #2654 的冻结 contract 要求 SM80 CuTe forward/backward；精确 head 因缺少
  `flash_attn_2_cuda` 与完整 CuTe 构建链未能进入数值测试，故保持 unresolved。

候选自带测试的代表性成功记录包括 Liger #1268 `56 passed`、verl #7013 `12 passed`、
slime #2205 `45 passed`、Megatron #5742 `12 passed, 5 skipped`、TorchTitan #3867
`9 passed, 2 subtests passed`。测试通过只说明对应测试范围成立，不自动等于 accept。

## 训练类判断经验

### 1. 技术 contract 与 disposition 必须拆开

Liger #1230、slime #2198/#2204、verl #6960/#6963/#7013 的技术 contract 均成立，但项目
处置为长期 open 或 closed-unmerged；反过来，多项有边界缺口的 technical check 最终 merged。
历史 disposition 还包含优先级、重复实现、维护节奏和项目治理，不能仅由局部 correctness 推断。
后续锁应同时保存：

- `technical_contract`: pass / bounded-gap / fail / unresolved；
- `disposition_prediction`: accept / check / reject；
- `governance_gap`: 两层不一致时保留差异，不用 outcome 反向改写技术事实。

### 2. 成熟历史队列不应滥用 disposition check

本队列 oracle check 为 0。对明显超出 30 天 prospective 窗口的样本，bounded technical gap
不能自动投影为 disposition check；若没有 outcome/review 泄漏地证明“新且正在处理”的资格，
历史处置层应作 accept/reject 预测。check 只留给真正的 prospective active-review 队列。

### 3. Reject 需要生产可达、可复现的阻断证据

本轮三个正确 reject 分别是语义 no-op、无法编译的 conflict head、默认 NCCL 下可复现的 CPU
broadcast 失败，均有明确 production path 或 exact-head 失败。verl #7014 则说明反面：LoRA+QAT
交集虽然源码可达，但缺少真实配置频率和项目支持边界证明，单凭邻接路径可能过度阻断。下一轮
reject 顺序应是配置合法性 → call-site reachability → exact counterexample → 修复规模。

### 4. 候选自带证据与 evaluator 证据要分层

候选测试、作者正文 benchmark、evaluator microbenchmark、精确 E2E 复现具有不同证明强度。
性能或显存 claim 不应因缺 evaluator E2E 就一律降 check，也不能因作者报告存在就视为独立复现。
下一轮把 candidate body 作为 outcome-free 输入单独哈希冻结，并显式标注 evidence tier。

### 5. 扩容不能把静态检查冒充完整 benchmark

后续计划总量为 200 个 PR（通信 50、训练 50、四个推理项目各 25），但从 R14 起严格按每组
30 个顺序推进；当前 R13 保持 29 个，不补样。每组必须完成揭示、误差审计和规则迭代后，下一组
才能冻结，避免把 200 个案例一次性锁死而失去逐轮学习。全部案例可以统一执行 exact-source
提取、语法/冲突/变更形状/测试归属检查，但 GPU 与 E2E 应按风险分层抽样并记录覆盖率；不能用
总样本量掩盖未运行的 contract。R14 首先评测 30 个通信类 PR。
