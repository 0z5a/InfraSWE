# R15：20 个通信类 + 10 个训练类历史 PR 盲测

## 结论

R15 达到“有提升再提交”的门槛。冻结判断在同一批 30 个 PR 上取得 `19/30`
exact（63.3%），同队列旧路数“技术 contract 通过则 accept，否则一律 check”为
`11/30`（36.7%），提升 26.7 个百分点。accept/non-accept 二分类为 `22/30`
（73.3%），与同队列旧路数相同。

本轮重点的 check/reject 区分明显改善：机器给出 3 个 check，命中 2 个，precision
为 66.7%；17 个 reject 中 10 个命中，precision 为 58.8%。20 个冻结非 accept 中，
新路数 exact 命中 12 个，旧路数只命中 4 个。机器锁定为 `10 accept / 3 check /
17 reject`；oracle 为 `12 accept / 4 check / 14 reject`。

R15 与 R14 的队列不同，因此 `19/30` 对 `11/30` 只能作为跨队列观察；可归因的提升是
R15 同一队列相对旧路数的 `+26.7 pp`。

R15 不使用权重分数，不能声称 merged PR 取得正式 `>=85` ProjectFit。技术 contract 与
历史 disposition 继续分别保留：TorchTitan #3522 与 verl #6593 有精确技术反例，但历史上
仍被合并；这类冲突不会被反向学习成“失败也应 accept”。

## 队列与盲测边界

R15 严格保持 30 例：20 个通信类完成通信 tranche，10 个训练类启动训练 tranche。选择
阶段只读取标题、changed paths、变更规模、创建时间和精确 base/head SHA；候选正文和源码
读取前已经冻结逐例 claim、matrix 和 closure。state、merge、review、comment、CI、label 均在
判断锁定后才读取。

4 个 SGLang 正文含动态 `pr-states` 区块。获取器在写入任何正文前确定性删除这些区块；仓库只
保存原始正文哈希、清洗后正文与逐块清洗记录，没有保存或使用原始区块内容。

远端使用 `2×NVIDIA A100-SXM4-40GB`。所有引用均切换到冻结的 `refs/r15/pr-*` 并校验
HEAD SHA。vLLM 源码检出缺少已编译扩展时使用 fail-closed import shim：只提供模块名称，
任何意外 kernel 调用仍会失败，不能伪造执行成功。

## 关键实测

- SGLang #37523 在两 rank NCCL 下各通过 4 个候选测试，覆盖 uneven、空 source、全空和
  deterministic combine。
- Megatron #7029 连续两轮创建 23 个辅助 process groups，销毁后 tracked/registered 均为 0；
  默认组和模型并行 collective 两 rank求和均为 3。
- TorchTitan #4399 用候选锁定的 `spmd_types==0.2.5`/`grain==0.2.18` 依赖通过 4 个测试；
  #3499 的双卡 NCCL mixed P2P 通过，但三卡 ring 与 TorchComms 未闭环。
- vLLM #54960 的 10 个 EC 单测和 1 个 scheduler aggregation 测试通过；#44583 的 mixed
  FA/MLA handshake 及 6 个 TP mapping 测试通过；#44495 连续绑定 32 个存活 ZMQ socket，
  得到 32 个唯一 `LAST_ENDPOINT`。
- slime #2011 在 `(8192, 32768)` BF16 entropy+backward 下，base peak delta 为
  `2,348,897,280` bytes（2.188 GiB），head 为 `1,073,775,616` bytes（1.000 GiB），
  同时 7 个正确性测试通过。
- slime #2304 的真实 CUDA phase probe 精确观察到 `67,108,864` bytes 分配，并在 finally
  路径报告 allocated/reserved peak。
- Liger #1405 的候选自带 sum-backward case 连续 3 次出现相同 31 个梯度 mismatch，是稳定
  exact counterexample。
- verl #6593 虽有 16 个正确性测试通过，但 `(8192,32768)` backward baseline peak delta 为
  `1,611,662,336` bytes（1.501 GiB），chunk 1024 为 `2,015,396,864` bytes（1.877 GiB），
  chunk 256 为 `2,099,280,896` bytes（1.955 GiB）；固定 chunk 256 时峰值随总 token 从
  2048 的 0.469 GiB 增至 16384 的 3.957 GiB，未实现“随 chunk 而非上下文缩放”的 closure。

### 锁内单位勘误

`machine-judgment-locks.json` 在解盲前已不可变地写入，因此不回改。verl #6593 的文字 finding
将上述两个十进制 byte 数误写为 `2.015–2.099 GiB`；正确换算是 `1.877–1.955 GiB`。原始
byte 证据、相对 baseline 更高的结论、decision 与所有哈希均不受影响。

## R16 前瞻迭代

R16 为 30 个训练类 PR。后续队列不提前选择，继续遵守“每 30 个结束后再迭代”。R16 冻结规则：

1. check 收紧到 `<=7` 天 hot window；若 exact core path 已过、只有一个 integration residual，
   coherent risk family 可放宽到最多 8 文件。
2. target-only 后端的 compile/import 或 mock orchestration 不再算 functional coverage；必须有目标
   numeric、progress、ordering 或 memory 证据。
3. 成熟多文件修改只有在“同一 backward-compatible 值机械传播至已枚举 adapters，端点测试通过，
   无 backend-specific 语义变化”时才可 accept。
4. 对只删除可证明冗余 copy/transpose、保持表示与控制流、且有目标 parity+benchmark 的成熟优化，
   允许 target-hardware transfer；新 kernel/新功能不适用。
5. exact 候选测试或资源反例始终优先于 disposition；merged 冲突记录为 oracle noise/governance debt。
6. 训练类 broad change 必须有 optimizer step、gradient、checkpoint 或 measured-memory closure；配置
   mock 通过不足以 accept。

剩余工作量为 `40 training + 100 inference`。R16 完成 30 个 training 后，再根据 R16 经验选择
下一组；不会提前污染未来队列。
